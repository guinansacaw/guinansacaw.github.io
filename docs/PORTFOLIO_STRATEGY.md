# PORTFOLIO_STRATEGY.md

## 1. Propósito

Este documento define la estrategia del portafolio profesional y sirve como fuente de verdad para futuras modificaciones del sitio, nuevos proyectos demostrables y trabajo asistido con Codex.

El objetivo principal es posicionar el perfil para conseguir proyectos freelance, especialmente en Upwork, relacionados con automatización de procesos, sistemas internos e integraciones.

---

## 2. Posicionamiento profesional

### Título actual

**Backend & Business Systems Engineer | Process Automation & Integration**

Este posicionamiento se mantiene.

La propuesta de valor no debe centrarse solamente en tecnologías. Debe comunicar la capacidad de convertir procesos manuales, hojas de cálculo y herramientas desconectadas en sistemas organizados y automatizados.

### Propuesta central

Construir soluciones de automatización e integración que pueden comenzar con herramientas low-code y escalar hacia backend personalizado cuando el problema lo requiera.

En términos prácticos:

- Airtable para datos estructurados y sistemas internos.
- Make para automatización e integración entre aplicaciones.
- Softr para interfaces y portales sobre datos de negocio.
- Azure, Node.js, SQL, APIs y webhooks cuando se necesita lógica personalizada, mayor control o integraciones más complejas.

### Diferenciación buscada

No competir únicamente como desarrollador backend ni únicamente como especialista low-code.

La diferenciación buscada es:

> Resolver procesos de negocio usando la herramienta adecuada: low-code cuando es suficiente y backend personalizado cuando el problema requiere más control, lógica o integración.

### Canal principal

**Upwork**

### Tipos de trabajo objetivo

Priorizar oportunidades relacionadas con:

- Airtable systems
- CRM setup and automation
- Lead management
- Business process automation
- Make.com workflows
- Internal tools
- Client portals
- Operations systems
- API integrations
- Webhooks
- ERP / CRM integrations
- Data synchronization
- Azure Functions and custom backend automation cuando el proyecto lo requiera

### Criterio de selección

Los proyectos del portafolio deben representar problemas que un cliente realmente podría publicar en Upwork.

No construir proyectos únicamente para mostrar tecnologías.

Cada proyecto debe responder a una pregunta comercial:

> ¿Qué problema de negocio demuestra que puedo resolver?

## 5. Portafolio objetivo

El portafolio principal estará compuesto por cuatro casos.

### 5.1 LoopyApp

**Tipo:** proyecto real / flagship project

**Rol dentro del portafolio:** demostrar profundidad técnica, arquitectura backend e integración de sistemas reales.

Debe evidenciar capacidades como:

- integración ERP;
- APIs REST;
- Azure Functions;
- Azure SQL;
- procesamiento operativo;
- reglas de negocio;
- webhooks;
- WhatsApp Business API;
- automatización de procesos;
- integración entre sistemas.

LoopyApp es la principal evidencia de que el perfil puede ir más allá del low-code cuando un problema requiere backend personalizado.

---

### 5.2 Freelance CRM & Project Operations System

**Tipo:** proyecto demostrable con utilidad real

**Usuario inicial:** el propio freelancer.

**Problema:** administrar leads, reuniones, clientes y proyectos sin depender de notas dispersas o recordar manualmente cada paso.

**Flujo conceptual:**

Lead → Discovery Meeting → Proposal → Client → Project → Milestones / Tasks → Delivery → Follow-up

**Stack objetivo:**

- Airtable
- Make
- Softr

**Capacidades que debe demostrar:**

- modelado relacional en Airtable;
- CRM básico;
- lead pipeline;
- discovery checklist;
- conversión de lead a cliente;
- creación y gestión de proyectos;
- milestones;
- tareas / Kanban;
- automatizaciones;
- portal o interfaz de operación.

Este proyecto debe ser utilizado realmente durante la actividad freelance para que pueda evolucionar con necesidades reales.

---

### 5.3 Sales CRM & Lead Automation

**Tipo:** proyecto demostrable orientado a demanda comercial.

**Problema:** una empresa recibe leads desde distintas fuentes y necesita centralizarlos, calificarlos y hacer seguimiento automáticamente.

**Flujo conceptual:**

Form / Scheduling Tool / Webhook → Make → Airtable CRM → Qualification → Pipeline → Follow-up / Notification

**Stack objetivo:**

- Airtable
- Make
- APIs / webhooks cuando aporten valor

**Capacidades que debe demostrar:**

- captura de leads;
- deduplicación;
- pipeline comercial;
- lead qualification;
- follow-ups;
- automatización de estados;
- integración con formularios o sistemas externos;
- sincronización de datos.

---

### 5.4 Inventory & Order Operations System

**Tipo:** proyecto demostrable orientado a operaciones.

**Problema:** una empresa necesita controlar productos, pedidos e inventario en un sistema centralizado y automatizar alertas o sincronizaciones.

**Flujo conceptual:**

Orders / External Source → Make → Airtable → Products / Orders / Inventory → Alerts / Operational Actions

**Stack objetivo:**

- Airtable
- Make
- APIs / webhooks

Softr puede incorporarse si agrega una interfaz útil, pero no es obligatorio.

**Capacidades que debe demostrar:**

- modelo de datos relacional;
- productos y SKU;
- órdenes;
- movimientos de inventario;
- stock;
- múltiples ubicaciones si el alcance lo permite;
- alertas de stock;
- lógica de negocio;
- automatización operacional.

## 6. Principios para los proyectos demostrables

Los proyectos no deben convertirse en startups ficticias ni productos enormes.

Cada proyecto debe ser:

- pequeño;
- terminado;
- demostrable;
- entendible rápidamente;
- basado en un problema de negocio reconocible;
- suficientemente completo para mostrar criterio profesional.

Un proyecto pequeño terminado tiene más valor para este objetivo que un sistema ambicioso incompleto.

### Definition of Done general

Un proyecto puede entrar al portafolio cuando:

1. el flujo principal funciona de extremo a extremo;
2. los datos están correctamente modelados;
3. las automatizaciones principales funcionan;
4. existe información de demostración segura;
5. existe una explicación clara del problema y la solución;
6. existen capturas o recursos visuales adecuados;
7. existe una demo en video cuando sea útil;
8. su case study está terminado.

---

## 7. Uso de video

Los videos serán parte de la estrategia del portafolio.

No deben ser tutoriales largos ni recorridos detallados de código.

### Duración objetivo

**1 a 3 minutos.**

### Propósito

Mostrar visualmente el flujo de negocio y el resultado de la solución.

Ejemplo para Freelance CRM & Project Operations System:

Lead registrado → preparación de discovery → conversión a cliente → creación automática del proyecto → milestones y tareas → portal / seguimiento.

Para LoopyApp, la demostración debe evitar datos sensibles y puede enfocarse en el recorrido conceptual del sistema y su arquitectura.

---

## 8. Niveles de presentación

Cada proyecto debe poder comprenderse en tres niveles:

### Portfolio card

Tiempo objetivo de comprensión: **10 segundos**.

Debe responder:

- qué problema resuelve;
- qué tipo de sistema es;
- tecnologías principales.

### Case study

Tiempo objetivo: **2 a 5 minutos**.

Debe explicar problema, solución, arquitectura, implementación y resultado.

### Video demo

Duración objetivo: **1 a 3 minutos**.

Debe mostrar el funcionamiento real o una demostración segura del flujo principal.

---

## 9. Honestidad técnica

No presentar como experiencia real aquello que solamente pertenece a un proyecto demostrable.

Distinguir claramente:

- proyectos reales;
- proyectos demostrables;
- tecnologías utilizadas directamente;
- tecnologías incorporadas para aprendizaje o actualización.

No usar títulos como "expert" para Airtable, Make o Softr hasta que exista evidencia suficiente para sostener esa afirmación.

---

## 10. Prioridad de ejecución

Orden recomendado:

1. Mantener LoopyApp como caso principal.
2. Construir Freelance CRM & Project Operations System.
3. Construir Sales CRM & Lead Automation.
4. Construir Inventory & Order Operations System.
5. Actualizar progresivamente el portafolio conforme cada caso esté terminado.

No publicar un proyecto nuevo como caso terminado antes de que exista una demo funcional y un case study coherente.
